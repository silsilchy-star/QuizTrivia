# birds 이미지 24장 육안 확인 + 문제 2장 교체 (2026-08-13)

인수인계에 "이 환경의 네트워크 제약으로 전량 확인 못 했음"으로 남아있던 항목을 끝냈다. **24장 전부 눈으로 확인하고 2장을 교체했다.**

## 확인 방법 — 429를 우회한 절차

사용자도 사진을 확인할 방법이 없다고 해서 양쪽이 막힌 상태였다. 다음 순서로 풀었다.

1. **Wikimedia API 일괄 조회** — URL 24개를 각각 GET하는 대신 `action=query&prop=imageinfo&titles=File:A|File:B|...`로 **요청 1번**. 레이트리밋을 아예 안 건드린다. `User-Agent` 지정은 필수(기본 curl UA는 막힘).
2. **썸네일 로컬 저장** — `iiurlwidth=300`으로 받은 CDN 썸네일을 내려받는다.
3. **Chromium으로 시트 렌더링** — `/opt/pw-browsers/chromium`이 사전 설치돼 있어 **playwright 패키지 설치가 필요 없다**(교훈 5번의 설치/제거 절차를 건너뛸 수 있다). 4열 × 6행 시트에 `id`·난이도·기대 학명·문항 본문을 캡션으로 붙여 한 장으로 렌더링.
4. **육안 확인** — 시트를 보고, 의심되는 건 원본 크기로 다시 본다.

이 절차는 `docs/question-authoring-standard.md` §8에 정리했다. **앞으로 76장을 채울 때 그대로 반복하면 된다.**

## 교체한 2장

### `bird-108` 왜가리 (*Ardea cinerea*, 난이도 2) — 답이 불가능한 문항이었다

기존 파일명:

```
Ardea cinerea - Grey heron - in a pond of Busan Citizens Park
with blue sky in Busan city South Korea.jpg
```

아파트 단지가 배경인 하천 전경 사진이고, 왜가리는 물속에 서 있는 작은 점이었다. 학명은 정확했지만 **"이 새의 학명은?"에 답할 수 없다.** 사진이 아니라 풍경이 출제된 셈이다.

**파일명이 이미 단서였다** — `with blue sky in Busan city`. 학명이 맞는지만 확인하고 넘어가면 이런 걸 놓친다. 기준 문서 §8에 "파일명에 장소·배경·풍경을 묘사하는 말이 있으면 풍경 사진일 가능성이 높다"로 적어뒀다.

→ `Ardea cinerea or the Grey Heron.jpg` (3456×2304)로 교체. 머리·부리·눈·목깃·날개깃이 모두 선명한 근접 사진.

### `bird-117` 꾀꼬리 (*Oriolus chinensis*, 난이도 3) — 화질·워터마크

새는 보였지만 파파야 잎에 가려 작고, 휴대폰 사진 화질에 **`2022.04.08 13:26` 날짜 스탬프가 이미지에 박혀** 있었다.

→ `Black Naped Oriole (6935459331).jpg` (4288×2848)로 교체. 파란 하늘 배경에 전신, 검은 뒷목띠와 붉은 부리가 선명.

두 교체 후보는 Commons 카테고리에서 **종횡비 1.6 이하 + 최소 800×600**으로 걸러 뽑았다(풍경 사진을 기계적으로 배제하는 방법). IUCN 분포도(`ArdeaCinereaIUCN2019 2.png`)가 후보에 섞여 나오므로 사람이 걸러야 한다.

검증: `npm run validate` 통과, 교체한 2개 URL 모두 API로 존재 확인(3456×2304 / 4288×2848).

## 썸네일 판단은 신뢰하면 안 된다

시트(썸네일 150px)만 보고 문제라고 의심한 5건 중 **3건이 오판**이었다.

| 문항 | 썸네일 판단 | 원본 확인 결과 |
|---|---|---|
| `bird-102` 까치 | 잎에 가려 보임 | **온전히 잘 보인다** — 나뭇가지에 전신 |
| `bird-106` 직박구리 | 뒷모습, 귀깃 안 보임 | **진단 형질인 갈색 귀깃까지 선명** |
| `bird-115` 황조롱이 | 뒷모습, 얼굴 안 보임 | **얼굴·반점까지 아주 좋은 사진** |
| `bird-108` 왜가리 | 풍경 사진 | 맞음 — 교체 |
| `bird-117` 꾀꼬리 | 가려짐·저화질 | 맞음 + 워터마크 발견 — 교체 |

**의심되면 반드시 원본 크기로 다시 본다.** 76장 검수 때도 같다.

## 교훈 6번 정정 — 429는 URL 방식 탓이 아니다

처음에는 `Special:FilePath`(MediaWiki 앱 서버 경유 302 리다이렉트)가 429의 원인이라 의심하고, CDN 직접 URL로 바꾸면 나아질 거라 생각했다. **틀렸다** — API로 받은 `upload.wikimedia.org` 썸네일도 똑같이 429가 났다(24장 중 10장 실패, 이후 4장 추가 실패 → 20초 간격 재시도로 전부 확보).

즉 레이트리밋은 **이 실행 환경의 공용 egress IP**에 걸린다. 실제 플레이어는 각자 다른 IP에서 스테이지당 5장을 보므로 해당되지 않는다.

→ **`Special:FilePath` 방식을 유지한다.** 오히려 Commons에서 파일 이름이 바뀌어도 따라가므로 링크가 덜 깨진다.

## 재시도 판정 함정

**429 응답이 HTML 에러 페이지(1966~2190 bytes)로 내려온다.** 처음에 "2000 bytes 초과면 성공"으로 판정했다가 **2190 bytes 에러 페이지 2개를 성공으로 잘못 세었다.** `file`로 `JPEG|PNG|WebP` 여부를 확인해야 한다. 기준 문서 §8에 적어뒀다.

## ⚠ 새로 드러난 미해결 문제 — 저작자 표시 의무

교체 후보의 라이선스를 확인하다 발견했다.

| 사진 | 라이선스 | 저작자 |
|---|---|---|
| `Ardea cinerea or the Grey Heron.jpg` | **CC BY-SA 4.0** | Ebla-ebla |
| `Black Naped Oriole (6935459331).jpg` | **CC BY 2.0** | Peter Gronemann |

둘 다 재사용은 가능하지만 **저작자 표시(attribution)가 요구되는 라이선스다.** 그런데 **앱은 사진의 출처·저작자를 어디에도 표시하지 않는다.**

이건 이번에 넣은 2장만의 문제가 아니라 **기존 24장 전체 + 앞으로 채울 76장에 해당**하고, 공개 서비스이므로 실제 라이선스 위반 소지가 있다. 내가 임의로 UI를 바꿀 범위가 아니라 **판단이 필요한 별도 항목으로 남겼다**(인수인계 7번, 기준 문서 §8 마지막). 최소 대응은 문항 해설이나 결과 화면에 저작자·라이선스를 한 줄 넣는 것이다.
