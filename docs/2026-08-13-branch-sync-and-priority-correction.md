# 브랜치 동기화 + 우선순위 정정 (2026-08-13)

새 세션이 인수인계 문서를 확인하는 것으로 시작했는데, 그 과정에서 **낡은 인수인계 문서를 읽고 있었다는 것**과 **문서 간 우선순위 모순**을 발견해 둘 다 고쳤다. 코드 동작 변경은 없다 — 배포 트리거·문서만 바뀌었다.

## 1. 세션이 8커밋 뒤처진 지점에서 시작했다

새 세션의 지정 브랜치 `claude/work-handover-file-check-zknp0b`는 `b329e61`("인수인계 문서 추가")에서 출발했다. 그런데 실제 최신 작업은 `claude/handover-matters-review-gs5597`의 `9dd5a54`까지 진행돼 있었다 — **8커밋 뒤처짐, 앞선 커밋 0개, 원격에는 브랜치가 아직 없음.**

즉 처음 읽은 `인수인계.md`는 P0·P1이 반영되기 전의 낡은 판이었다. 낡은 판에는 예를 들어 "birds 56문항 더 필요"(실제로는 게이트가 난이도 1~5로 확장되면서 76개), "공식 3주제 각 80문항"(실제로는 100문항)처럼 지금과 다른 서술이 들어있었다.

### 그대로 진행했다면 생겼을 사고

`deploy.yml` 트리거에는 `repo-permissions-check-ff2du7`와 `handover-matters-review-gs5597`만 있었고 **새 세션의 브랜치는 없었다.** 두 가지로 깨진다.

1. **그냥 push** → 트리거에 없으니 아무 일도 일어나지 않는다. 배포된 줄 알고 넘어간다.
2. **트리거에 새 브랜치를 추가하고 push** → 이게 실제 사고다. 파이프라인이 stale JSON으로 `build:seed`를 돌리고, 생성된 SQL에 이 문장이 들어간다.
   ```sql
   DELETE FROM questions WHERE author_uid IS NULL AND id NOT IN (<JSON의 id 목록>);
   ```
   stale JSON에는 난이도5 문항 60개가 없으므로 **프로덕션에 살아있는 난이도5 문항 60개가 삭제된다.** 게이트도 구(1~4) 기준으로 재판정되어 주제는 그대로 `active`로 남는다 — **에러 없이 콘텐츠만 조용히 롤백**되므로 발견이 매우 어렵다.

### 조치

- `git checkout -B claude/work-handover-file-check-zknp0b 9dd5a54` — 앞선 커밋이 0개라 유실 없이 안전.
- `deploy.yml` 트리거를 `work-handover-file-check-zknp0b` + `handover-matters-review-gs5597`로 정리. **완전히 폐기된 `repo-permissions-check-ff2du7`은 제거**했다(P0의 "배포 브랜치 정리"에서 남겨뒀던 것). 이전 세션 브랜치는 그 세션이 아직 살아있을 수 있어 남겨뒀다 — **다만 두 브랜치가 동시에 트리거에 있으면 나중에 push한 쪽이 프로덕션을 덮으므로 배포 경합 위험이 있다.**
- 인수인계 문서에 **"새 세션은 자기 브랜치가 (a) 최신 커밋에서 출발했는지 (b) `deploy.yml` 트리거에 있는지를 가장 먼저 확인할 것"**을 명시. 세션마다 브랜치가 새로 생기는 구조라 이 사고는 반복될 수 있다.

## 3. 인수인계 문서와 PLAN4의 우선순위가 모순이었다

`인수인계.md`의 "남은 일"은 PLAN4 신규 항목들을 **6번(후순위)** 에 뒀다. 그런데 `PLAN4.md` §7은 같은 항목들을 **`P-1 (신규, 최우선)`** 으로 올려놓고 "P0보다 먼저, 또는 병행"이라고 못박아뒀다. 근거까지 적혀 있다.

> 문항 작성 기준 문서는 **P1(콘텐츠 대량 작성)보다 먼저** 있어야 새로 쓰는 문항이 처음부터 기준을 따른다.

이 순서를 어기면 **birds 76문항을 기준 없이 쓰고 나서 재작업**하게 된다. `PLAN4.md` §7을 정본으로 삼아 인수인계 문서의 순서를 정정했다.

## 4. "정답 피드백 부족"은 단독 수정 대상이 아니다

`PLAN4.md` §1이 "코드로 확인된 실제 결함"으로 분류한 항목이라 코드를 직접 확인했다. **결함은 실재한다** — `src/App.tsx`의 `Quiz` 컴포넌트는 스테이지 5문항을 전부 답해야 `제출` 버튼이 뜨고(마지막 문항 버튼이 `isLast ? '제출' : '다음'`), 그제서야 `StageResult`가 5문항 전체의 정답·해설을 한꺼번에 보여준다. 1번 문항을 맞았는지 5번까지 다 풀어야 안다.

그런데 `PLAN4.md` §2는 이미 스스로 갱신되며 결론을 내려놨다 — **PLAN3 보드 모드가 "문항 1개씩 즉시 채점"으로 설계돼 있어 이 문제를 그대로 해결하므로 별도 작업 불필요.** 스테이지 판 자체가 폐지 확정(PLAN3 §9)이라 결함을 가진 모드가 사라진다. 타워에도 같은 문제가 재발할 뻔한 것은 **"1층 = 1문항, 즉시 채점"**으로 미리 막아뒀다(PLAN2 §8 ⑪).

→ 지금 이걸 따로 고치면 **P2에서 통째로 삭제될 코드를 고치는 낭비**다(`difficultyForStage()` 같은 죽은 코드를 미리 손대지 말라는 것과 같은 논리). **P2 우선순위를 올리는 근거로만 쓴다.** 인수인계 문서에 이 판단을 적어뒀다.

## 5. birds 76문항 작업에 대해 새로 확인된 제약

- **`data/topics.json`의 birds `difficultySpec`은 난이도 1~5가 이미 다 채워져 있다.** 이전 인수인계 판은 "1~4만 있음, 5는 아직 안 씀 — birds가 5단계까지 필요한지도 처음 확인해볼 것"이라고 적었는데 사실이 아니었다. 스펙 작성 단계는 불필요하다.
- **`validate`가 이미 경고 중**: `birds: NUMERIC_INPUT 비율 0% — 목표 20~25% 미달`. 이미지 맞추기 주제라 객관식/단답형에 쏠려 있다. 76개를 채울 때 숫자입력을 어떻게 섞을지 먼저 정해야 경고가 안 남는다.
- 기존 24문항에도 품질 경고가 있다 — `bird-113`~`bird-118`은 난이도3인데 `seedRef`가 없다. P-1 기준 문서를 만들 때 같이 정리하는 게 자연스럽다.
- **이미지 URL 검증은 이 환경에서 여전히 막힌다** — 표본 3장 중 2장이 429(교훈 6번 재현). 76개를 만들기 *전에* 기존 `Special:FilePath` 방식이 실제로 잘 뜨는지 표본 몇 장을 사용자에게 먼저 확인받으면, 같은 실수로 76개를 다시 만드는 일을 막을 수 있다.
