# 창작마당 주제 소실 조사 — 결론: 이 세션 이전에 사라졌음

## 무슨 일이 있었나

토대 작업(`282f18a` → `7bc23fd`)을 배포한 뒤 사용자가 프로덕션을 확인하다가, 창작마당에 주제가 **"동물" 하나만** 보인다고 알려왔다. 인수인계 문서(`b329e61`, 06:59 작성)에는 **"사용자가 만든 주제 4개가 프로덕션에 있음(그중 '칵테일, 주류'는 문항 5개)"** 이라고 적혀 있었다.

세션 처리·스키마 베이스라인·레이트리밋을 연달아 바꾼 직후였으므로, 내 변경이 원인일 가능성을 먼저 의심해야 했다.

## 1차 — 코드로 배제

배포 경로에서 커뮤니티 데이터를 지울 수 있는 지점을 전부 훑었다.

| 지점 | 판정 |
|---|---|
| 새 `db/schema.sql` | 전부 `CREATE TABLE IF NOT EXISTS` — 삭제문 없음 |
| `build-seed.mjs`의 `DELETE FROM questions` | `author_uid IS NULL`로 공식 문항에만 걸림 |
| `build-seed.mjs`의 `DELETE FROM question_topics` | 같은 범위 제한 |
| `INSERT OR REPLACE INTO topics` | `data/topics.json`의 id만 대상 — 커뮤니티는 uuid |
| `handleDeleteCommunityTopic` | 작성자 본인의 명시적 호출로만 동작 |

구조상 배포가 커뮤니티 주제를 지울 수 없다. 다만 이것만으로는 "안 지웠다"의 증명이 못 된다.

## 2차 — 프로덕션 현재 상태

배포 워크플로에 집계 단계를 추가해(아래 참고) 실제 수치를 찍었다.

```
official_active: 3     community_topics: 1     community_questions: 0
official_questions: 264   users: 16   users_linked: 8   runs: 38   topic_best: 10
```

**`community_questions`가 정확히 0**인 것이 결정적이었다. 만약 배포가 주제만 지웠다면 문항은 남아 **고아 행**이 됐을 것이고(배포 스크립트는 `questions`를 `author_uid IS NULL`로만 건드리므로), 테이블이 통째로 날아갔다면 주제에 `q_count`가 남은 채 문항만 사라졌을 것이다. 실제 상태는 주제·문항·연결이 모두 짝을 맞춰 사라진 모습 — 앱의 삭제 기능이 만드는 바로 그 형태다.

그래도 "사라진 시점"은 알 수 없었고, 사용자도 직접 지웠는지 기억하지 못했다.

## 3차 — 백업으로 확정

배포 파이프라인이 DB를 바꾸기 직전에 남기는 D1 백업 아티팩트를 열었다. 임시 워크플로를 만들어(`backup-inspect.yml`, 확인 후 삭제) 백업을 실제 SQLite에 적재하고 쿼리했다.

> 처음엔 `grep`으로 세려다 `runs`/`users`가 0으로 잘못 나왔다. D1 export의 INSERT 형식을 넘겨짚은 탓이다. 형식을 추측하지 말고 적재해서 쿼리해야 한다.

**14:10 시점 백업 — 이 세션이 프로덕션 DB를 처음 건드리기 직전:**

```
커뮤니티주제  커뮤니티문항  유저  플레이기록  주제최고점
     1            0        15      38         10

동물   draft   2026-08-13T06:32:32.415Z   문항 0개
```

**이미 그때부터 "동물" 하나뿐이었다.** 이 세션의 작업이 시작되기 전에 사라진 것이다.

### 배포 전후 대조

| | 14:10 (작업 전) | 15:21 (지금) |
|---|---|---|
| 커뮤니티 주제 | 1 | 1 |
| 커뮤니티 문항 | 0 | 0 |
| 유저 | 15 | 16 (사용자가 새 데스크톱에서 접속) |
| 플레이 기록 | 38 | 38 |
| 주제별 최고점 | 10 | 10 |

**배포 세 번을 거치는 동안 사용자 데이터가 한 건도 변하지 않았다.** 스키마 베이스라인 통합과 세션 서명 도입이 기존 데이터에 무해했다는 실증이기도 하다.

## 언제 사라졌는지는 특정할 수 없다

06:59(인수인계 문서 작성, 주제 4개)와 14:10(주제 1개) 사이다. 그 구간의 배포는 전부 **다른 작업 세션의 브랜치**에서 옛 워크플로로 돌았다(10:03, 10:13, 11:02, 11:07, 11:19, 11:30, 11:49 — 총 7회). 옛 워크플로에는 백업 단계가 없어서 **그 시점의 스냅샷이 존재하지 않는다.**

즉 원인을 더 좁힐 근거가 남아있지 않다. 가능성은 두 가지다:
1. 사용자가 삭제 기능으로 직접 정리했다 (현재 상태가 이것과 정확히 일치한다)
2. 그 구간의 배포/작업 중 무언가가 지웠다 (근거 없음 — 다만 배제할 자료도 없다)

**증거가 없는 쪽을 단정하지 않는다.** 다만 이 조사에서 확실한 것은 하나다 — 백업이 없으면 이런 질문에 답할 수 없다.

## 이 조사가 남긴 것

배포 워크플로에 **DB 변경 직전/직후 집계**를 상설로 추가했다.

```yaml
- name: Count rows (before)   # schema/migrations/seed 적용 직전
- name: Count rows (after)    # 배포 직후
- name: List community topics # 커뮤니티 주제 목록까지
```

앞으로는 두 수치를 비교하는 것만으로 **그 배포가 사용자 데이터를 건드렸는지** 즉시 판별되고, 배포끼리 비교하면 언제 줄었는지도 좁혀진다. 남아있던 "에러 로깅/관측" 항목의 가장 값싼 첫 조각이다.

집계 쿼리는 처음에 `UNION ALL`을 8개 쌓았다가 D1에 거부당했다(`too many terms in compound SELECT`). 스칼라 서브쿼리로 한 행에 담는 방식으로 고쳤고, 이번엔 푸시 전에 로컬 D1에 같은 명령을 그대로 돌려 확인했다 — **워크플로의 쉘 명령은 테스트가 덮지 못하는 영역**이라 직접 실행해보는 수밖에 없다.

## 부수 확인 — 로그인은 정상

같은 화면에 "이 구글 계정은 이미 다른 기록과 연결되어 있어 그 계정으로 전환했습니다" 배너가 떠 있었다. 확인 결과 사용자가 **다른 데스크톱으로 옮겨서** 쿠키가 없는 상태로 접속해 새 익명 세션이 생겼고, 구글 로그인 시 기존 계정으로 전환된 것이다. PLAN 5.4절 계정 승계가 의도대로 동작한 결과이며 버그가 아니다. `users`가 15→16으로 늘어난 것도 이 접속분이다.

## 검증

- 프로덕션 현재 집계와 대조
- 임시 워크플로는 확인 후 삭제
