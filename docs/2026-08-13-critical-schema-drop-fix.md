# ⚠ 긴급 — 배포마다 users/runs/topic_best가 통째로 지워지던 버그

## 완료 판정
> 유저 창작마당 기능을 설계하려고 `db/schema.sql`을 다시 읽다가 발견. 즉시 고쳐서 배포했다.

## 무엇이 잘못됐었나
Day 6(`790ecda`)에서 `users`에 `google_sub`/`email` 컬럼을 추가할 때, FK 제약 때문에 `runs`/`topic_best`/`topic_best_weekly`/`users`를 **DROP 후 재생성**하는 방식을 썼다. 스스로 주석에 "이 시점엔 테스트 계정·판밖에 없어 안전 — 진짜 사용자가 생긴 뒤엔 이런 DROP 금지"라고 적어놓기까지 했는데, **정작 진짜 사용자(구글 계정)가 생긴 뒤에도 그 DROP 문을 지우는 걸 잊었다.**

`db/schema.sql`은 `.github/workflows/deploy.yml`이 **배포할 때마다 무조건 실행**한다. 즉 Day 6 이후 이 브랜치에 푸시된 배포(랭킹 보드 `e6d5a07`, 헤더 CSS 수정 `e9df823`, 로그인 캐시 수정 `8d46b5d` — 총 3회) **전부가 매번 `users`/`runs`/`topic_best`/`topic_best_weekly`를 통째로 비우고 재생성했다.**

## 영향
사용자가 실제로 연결한 구글 계정(`google_sub`)·닉네임·플레이 기록(`topic_best`, `runs`)이 그 사이 배포 시점마다 지워졌을 수 있다. 사용자가 "판을 끝냈는데 랭킹에 점수가 안 보인다"고 보고한 것의 실제 원인이 (스테이지 중간에 멈춘 것이 아니라) 이 버그였을 가능성이 있다.

## 무엇을 고쳤나
`DROP TABLE IF EXISTS` 네 줄을 전부 제거하고, 해당 네 테이블의 `CREATE TABLE`을 `CREATE TABLE IF NOT EXISTS`로 바꿨다. 컬럼 구성 자체는 지금 라이브 상태와 동일하므로(이미 그 DROP+재생성이 마지막으로 실행됐을 때 이 컬럼들이 만들어짐), 이 전환은 데이터를 잃지 않고 안전하다.

**앞으로 이 네 테이블의 스키마를 바꿔야 하면 반드시 `ALTER TABLE ... ADD COLUMN` 마이그레이션만 쓴다. DROP은 다시 쓰지 않는다.**

## 검증
- 로컬 D1에 재적용해 idempotent함을 확인 (에러 없이 통과, 기존 로컬 데이터 보존).
- 원격 배포(GitHub Actions) 성공 확인.

## 남은 일
사용자에게 로그인 상태·닉네임이 남아있는지 확인 요청함 — 지워졌다면 재로그인/재설정 필요, 이후로는 더 이상 지워지지 않는다.
