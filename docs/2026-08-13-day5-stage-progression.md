# Day 5 — 스테이지 진행 (게임성)

## 완료 판정 (PLAN 8장)
> "주제를 골라 12스테이지까지 갈 수 있다"

**충족.** 12스테이지 전부 정답 제출 시 최종 점수 **1500점**(PLAN 5.1절 만점)이 정확히 나온다.

## Day 2 대비 무엇이 달라졌나
Day 2는 "5문항 한 판"이 전부였다 — 스테이지 개념이 없고 모든 난이도가 뒤섞여 출제됐다. Day 5에서 PLAN 4.1·4.2절의 실제 코어 루프를 구현했다:

```
스테이지 N 진입 → 문제 5개 (난이도 = f(N)) → 4개 이상 정답 → 스테이지 N+1
                                          → 3개 이하 정답 → 판 종료
스테이지 12 클리어 → 판 종료 (만점)
```

난이도 매핑: 1–3→1, 4–6→2, 7–9→3, 10–12→4 (PLAN 4.2절 그대로).

## API 변경
`POST /api/runs`는 이제 스테이지 1만 출제한다. `POST /api/runs/:id/submit`이 스테이지 채점 + 다음 스테이지 출제를 한 응답에서 같이 처리한다:
- 클리어 & 스테이지 남음 → `nextStage: { stage, questions }` — 클라이언트가 별도 fetch 없이 바로 이어감
- 클리어 실패, 또는 12스테이지 완주 → `runOver: true, final: {...}` — 여기서만 `topic_best`/`users.global_score` 갱신

## DB 스키마 변경 — `runs` 테이블 재생성
스테이지 진행 상태를 담으려 컬럼을 늘려야 했다: `all_served_json`(판 전체에서 지금까지 낸 문항, PLAN 4.3절 "판 내 무중복"을 12스테이지에 걸쳐 지키기 위함). `CREATE TABLE IF NOT EXISTS`로는 기존 원격 테이블에 컬럼이 안 늘어나므로 `DROP TABLE IF EXISTS runs`를 먼저 실행하도록 했다.

**이건 지금만 괜찮다.** 아직 내 테스트 판 몇 개 말고는 `runs`에 데이터가 없다. 진짜 사용자가 생긴 뒤에 스키마를 바꿔야 한다면 이런 DROP은 금지이고 `ALTER TABLE` 마이그레이션으로 가야 한다 — 이 판단 자체를 코드 주석에 남겨뒀다.

## 검증

로컬 `wrangler dev`:

| # | 케이스 | 결과 |
|---|---|---|
| 1 | 12스테이지 전부 정답 | 최종 1500점, `stagesCleared=12` ✅ |
| 2 | 스테이지 4에서 진입해 성공(누적 250점) 확인 | 스테이지 1–3(난1)×3×50 + 스테이지4(난2)×100 = 250점 — 난이도 매핑이 스테이지 3/4 경계에서 정확히 바뀜 ✅ |
| 3 | 스테이지 5에서 실패 | `stagesCleared=4`, `totalScore=250` 그대로 확정, `runOver=true` ✅ |
| 4 | 실패 후 이전 최고기록(1500) 유지 | `topicBestScore=1500`, `isNewBest=false` — 낮은 점수 판이 최고기록을 덮지 않음 ✅ |
| 5 | 12스테이지 내내 판 전체 무중복 | 매 스테이지 `all_served_json` 대조, 중복 0건 ✅ |
| 6 | 종료된 판에 재제출 | 409 ✅ |
| 7 | 다른 uid로 남의 판 접근 | 404 (쿠키 세션과 무관한 판은 아예 안 보임) ✅ |

브라우저(Playwright)로 스테이지 1 실패 시나리오를 실제 클릭으로 관통 — 스테이지 배너("과학 · 스테이지 1/12 · 난이도 1 구간")→ 5문항 오답 유도 → 스테이지 실패(2/5)로 즉시 최종 결과 화면("스테이지 0까지 클리어", 20점)까지 확인. 검증용 playwright는 다시 의존성에서 제거.
