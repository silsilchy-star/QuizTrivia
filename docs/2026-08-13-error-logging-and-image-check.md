# 런타임 에러 기록 + 이미지 검수 페이지

토대에 마지막으로 남아있던 "에러 로깅/관측"을 채우고, 콘텐츠 작업(새 맞추기 56문항)의 전제인 이미지 검증 수단을 만들었다. 두 작업은 서로 독립적이라 한 번에 처리했다.

## ① 런타임 에러 기록 (`worker/errorlog.ts`)

### 무엇이 문제였나
워커가 예외를 던지면 **그 사실 자체가 아무데도 남지 않았다.** 사용자가 "이상하다"고 말해줘야 알았고, 실제로 오늘도 창작마당 건을 그렇게 알았다. Cloudflare 대시보드 로그는 실시간 tail이라 지나가면 사라진다.

### 무엇을 했나
라우팅 전체를 `try/catch`로 감싸고, 잡힌 예외를 D1 `error_log`에 남긴다. 레이트리밋과 같은 방식이라 나중에 조회·집계할 수 있다.

```ts
export default {
  async fetch(request, env, ctx) {
    try {
      return await route(request, env);
    } catch (error) {
      ctx.waitUntil(logError(env, request, error));
      return json({ error: 'internal error' }, { status: 500 });
    }
  },
};
```

기존 라우팅 본문은 `route()`로 빼냈다. 동작은 그대로다.

### 설계에서 신경 쓴 것

- **`ctx.waitUntil`로 기록한다.** 로그를 쓰느라 사용자 응답이 늦어지면 안 된다.
- **응답에는 내부 정보를 담지 않는다.** 사용자는 `{"error":"internal error"}`만 받고, 스택은 `error_log`에만 남는다.
- **쿼리스트링을 버리고 경로만 남긴다.** `/api/auth/google/callback?code=...`의 `code`처럼 그대로 남기면 안 되는 값이 섞인다.
- **메시지 500자·스택 2000자로 자른다.** 원인 파악에는 앞부분이면 충분하고, 한 행이 DB를 잡아먹으면 안 된다.
- **로깅 실패는 통째로 삼킨다.** 로깅 때문에 요청이 깨지는 것이 원래 에러보다 나쁘다.
- **500행 상한.** 5% 확률로 오래된 것부터 정리한다(레이트리밋과 같은 기회주의적 방식 — 별도 cron을 두지 않는다).

배포 로그의 집계(`Count rows`)에도 `errors` 항목을 넣었다. 배포할 때마다 누적 에러 수가 찍히므로, 갑자기 늘면 바로 눈에 띈다.

### 테스트 (11개)
- 예외의 이름·메시지·스택과 요청 정보가 남는가
- Error가 아닌 값을 던져도 기록되는가
- **쿼리스트링이 버려지는가** (`code=SECRET`이 안 남는지 직접 확인)
- 긴 메시지·스택이 잘리는가
- **기록에 실패해도 예외를 밖으로 던지지 않는가** (`prepare()`가 던지는 가짜 DB로 확인)
- **실제로 예외가 나는 경로에서 500이 나오고 로그가 남는가** — `runs.served_json`을 깨뜨려 `JSON.parse`가 던지게 만들어 확인했다. 응답 본문에 `SyntaxError`나 `served_json`이 새지 않는 것까지 봤다.
- 404, 정상 요청, 깨진 JSON 본문은 **에러로 기록되지 않는가** — 정상 트래픽이 로그를 더럽히면 진짜 장애를 못 찾는다

## ② 이미지 검수 페이지 (`scripts/build-image-check.mjs`)

### 왜 필요했나
새 맞추기(birds)는 24/80 문항이고 전부 이미지 문항인데, **그 이미지들이 실제로 뜨는지 아직 아무도 확인하지 못했다.** 이 작업 환경은 `commons.wikimedia.org` 접근이 프록시 정책상 차단돼 있어(`HTTP 000 / CONNECT tunnel failed 403` 확인) 여기서는 검증할 수 없다.

56문항을 더 만든 뒤에 이미지 방식에 문제가 있다는 걸 알면 80개를 다 고쳐야 한다. **24개일 때 확인하는 것이 훨씬 싸다.**

### 무엇을 했나
`data/questions/*.json`의 이미지 문항을 한 페이지에 늘어놓는 정적 페이지를 생성한다. 배포되면 `/image-check.html`로 열린다.

**눈으로 24장을 훑게 하지 않는다.** `<img>`의 load/error를 세어서 맨 위에 결과만 띄운다:
- 전부 정상 → "✅ 24장 전부 정상입니다"
- 실패 있음 → "⚠️ 24장 중 N장이 깨졌습니다" + 깨진 문항 id 목록

사람은 요약 한 줄만 읽으면 된다.

> 처음엔 인라인 `onload`/`onerror`를 썼는데, 그러면 하단 스크립트가 돌기 전에 로드가 끝난 이미지가 두 번 집계된다. 리스너를 스크립트에서만 붙이고 이미 끝난 것은 `img.complete`로 가려내도록 고쳤다.

`npm run build`에 포함시켜 항상 최신 문항을 반영하고, 생성물은 gitignore한다.

## 검증
- `npx tsc -b` 통과
- `npm test` — 127개 전부 통과 (에러 로깅 11개 추가)
- 빈 D1에 `schema.sql`만으로 `error_log` 테이블까지 생성 확인
- 배포용 집계 쿼리를 **로컬 D1에 그대로 실행**해 확인 (워크플로 SQL은 테스트가 못 덮는 영역 — 지난번 `UNION ALL` 사고의 교훈)
- `npm run build` → `dist/image-check.html` 생성 확인, 워커 번들 dry-run 통과

## 남은 일
- **사용자가 `/image-check.html`을 열어 결과 확인** → 이 결과가 다음 순서를 정한다
  - 전부 정상 → 새 맞추기 56문항 진행
  - 깨진 것 있음 → R2 자체 호스팅으로 전환 후 진행
- `worker/session.ts`의 `ACCEPT_LEGACY` 닫기 (전환 기간 후)
- 정답률 기반 난이도 보정 (데이터가 더 쌓인 뒤 — 현재 38판)
