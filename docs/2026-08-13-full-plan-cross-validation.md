# PLAN2/3/4 전체 교차검증 — 통합 랭킹·시즌제 폐기, 타워 단일화

2026-08-13. 구현은 아직 없다. PLAN2.md·PLAN3.md·PLAN4.md 수정만 담은 커밋.

## 왜

"플랜들 전부 교차 검증하고 명확하지 않은 부분이나 우려되는 부분 질문으로
해소"라는 요청으로, 세 문서를 코드와 다시 대조했다. 사소한 정합성 문제(오래된
상호 참조, 로드맵 표에 P-1 누락)는 바로 고쳤고, 구조적인 문제 5개는
AskUserQuestion으로 확인받았다.

## 가장 중요한 발견: 통합 랭킹이 topic_best의 파생값이었다

`worker/index.ts`의 `finalizeRun()`을 다시 읽다가, `users.global_score`가
독립된 값이 아니라 `SUM(topic_best.score) WHERE uid=?`로 계산되는 **파생값**
이라는 걸 확인했다. `topic_best_weekly`(주간 보드의 근거)도 같은 함수에서만
갱신된다.

그런데 `topic_best`를 채우던 유일한 게임 모드는 C2(구 스테이지 판)였고, 이미
PLAN3에서 완전 폐지가 확정된 상태였다. 새로 추가되는 두 모드는 둘 다
`topic_best`를 안 건드린다 — 보드 모드는 의도적으로 랭킹 미반영(PLAN3 §6),
타워는 여러 주제를 섞어서 "주제 하나"를 전제하는 `topic_best` 모델과 안 맞는다.

즉 **"주제별 순위 화면을 어떻게 할까"라는 작은 질문으로 물었던 게, 사실은
"통합 랭킹(전체기간·주간) 전체가 데이터 원천을 잃는다"는 훨씬 큰 문제였다.**
처음 질문에는 이 파급 효과를 옵션 설명에 못 넣어서, 답변을 받은 뒤 다시
설명하고 재질문했다.

## 연쇄적으로 이어진 결정들

1. **통합 랭킹 보드(전체기간·주간) 폐지.** 랭킹은 타워 층수 하나만 남는다.
2. **시즌제 폐기.** 시즌제를 도입한 유일한 이유가 "난이도5로 만점이 바뀌어
   점수 합산형 랭킹이 옛 기록과 새 기록을 섞는다"는 문제였는데, 그 랭킹 자체가
   없어지면서 이유도 사라졌다. 타워의 지표(도달 층수)는 만점 개념이 없어
   난이도5가 추가돼도 이 문제가 발생하지 않는다.
3. **업적은 타워 플레이만 인정.** 보드 모드는 `finalizeRun()`을 안 거치므로
   원래 설계대로면 업적에 안 잡힐 뻔했다 — 순수 연습으로 완전히 분리하는
   쪽으로 정리했다.
4. **타워 1층 = 1문항, 즉시 채점.** PLAN2 원문의 "최근 10층(50문항)" 같은
   표현을 역산하면 층당 5문항이 암묵적으로 전제돼 있었는데, 이러면 보드
   모드가 막 해결한 "5문항을 다 풀어야 정답 여부를 안다"는 배치 피드백
   문제가 타워에 그대로 재발할 뻔했다.

## 파급 효과 — P0가 크게 가벼워졌다

시즌제가 없어지면서 `topic_best` PK 확장(테이블 재생성)이 통째로 불필요해졌다.
**P0의 위험한 테이블 재생성이 2건(`questions` CHECK, `topic_best` PK)에서
1건(`questions` CHECK)으로 줄었다.** `topic_best`/`topic_best_weekly`/
`users.global_score`는 지우지 않고(DROP 금지 원칙) 그냥 더 이상 안 쓰는
동결된 역사 기록으로 남긴다.

## 부수 발견 — 직접 정하고 넘어간 것

타워는 여러 주제를 섞는데 `runs.topic_id`가 `NOT NULL`이라 스키마와 안
맞았다. `runs` 테이블 자체를 타워에서 재사용하지 않고 전용 `tower_progress`
테이블(진행 층·최고 층·현재 문항·최근 무중복 목록)을 따로 두는 것으로
해소했다 — 스키마 변경이나 별도 확인 없이 진행 가능한 사소한 판단이라 직접
정했다.

또한 커뮤니티 주제가 보드 모드로 플레이된다는 점도 확인했다 — 커뮤니티
주제는 항상 세부 장르가 없는 `broad`라서, PLAN3가 이미 설계해둔 "새 맞추기"
같은 폴백 케이스와 완전히 같은 방식으로 자동으로 커버된다. 별도 설계 불필요.
