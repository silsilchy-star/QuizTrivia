# 레이트리밋 — 어뷰징 방어

토대 다지기의 마지막 조각. 이 서비스에는 **제한이 한 곳도 없었다.**

## 무엇이 문제였나

가장 큰 구멍은 `/api/session`이었다. 쿠키 없이 부를 때마다 `users` 행을 하나씩 만든다:

```ts
const uid = crypto.randomUUID();
await env.DB.prepare('INSERT INTO users (uid, is_anonymous, ...) VALUES (?, 1, ...)')
```

인증도 제한도 없으므로, 이 엔드포인트를 반복 호출하는 것만으로 D1의 행 한도를 채워 **서비스를 통째로 멈출 수 있었다.** 창작마당 주제·문항 생성, 판 시작에도 개수 제한이 없었다.

## 무엇을 했나

`worker/ratelimit.ts` — D1에 카운터를 두는 고정 창(fixed window) 방식.

```sql
CREATE TABLE IF NOT EXISTS rate_limits (
  bucket     TEXT PRIMARY KEY,   -- "<행동>:<주체>:<창 시작시각>"
  count      INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);
```

카운터 증가와 조회를 한 번의 쿼리로 한다:

```sql
INSERT INTO rate_limits (bucket, count, expires_at) VALUES (?, 1, ?)
ON CONFLICT(bucket) DO UPDATE SET count = count + 1
RETURNING count
```

| 대상 | 주체 | 한도 |
|---|---|---|
| 새 익명 계정 생성 | IP | 100 / 시간 |
| 판 시작 | uid | 120 / 시간 |
| 창작마당 주제 생성 | uid | 10 / 일 |
| 창작마당 문항 추가 | uid | 300 / 일 |

한도를 넘으면 `Retry-After` 헤더를 붙인 429를 준다.

### 설계에서 신경 쓴 것

- **새 계정을 만드는 경로만 제한한다.** 기존 세션을 확인만 하는 `/api/session` 경로는 제한하지 않는다 — 정상 사용자가 새로고침으로 막히면 안 된다.
- **공용 NAT를 고려했다.** 한 교실에서 다 같이 처음 들어오는 상황이 막히면 안 되므로 IP당 100/시간으로 넉넉히 잡았다. 스크립트로 긁는 쪽은 이보다 훨씬 빠르므로 이 정도로도 충분히 걸린다.
- **CF 헤더가 없어도 무제한이 되지 않는다.** `CF-Connecting-IP`가 없으면 `unknown`이라는 고정 키로 묶어서라도 센다.
- **권한 검사가 먼저다.** 창작마당은 `requireAuthor` 뒤에 제한을 건다 — 로그인하지 않은 요청이 남의 한도를 소모하면 안 된다.
- **별도 정리 작업(cron)을 두지 않았다.** 만료된 행은 1% 확률로 기회주의적으로 지운다.

### Cloudflare 네이티브 rate limiting을 안 쓴 이유

로컬 테스트에서 재현하기 어려워, "불변식은 테스트로 못을 박는다"는 이 프로젝트의 방향과 어긋난다. 지금 규모에서는 D1 쓰기 한 번이 문제되지 않는다. 트래픽이 커지면 그때 바꿔도 이 모듈의 인터페이스는 그대로다.

## 테스트가 드러낸 것 — 테스트 환경의 함정

`test/ratelimit.test.ts`(15개)를 붙이고 나서 **다른 테스트가 간헐적으로 깨지기 시작했다.** 한 번 돌리면 통과하는데, 상태를 지우지 않고 세 번째로 돌리면 무관한 테스트가 실패했다.

원인을 파보니 이 테스트 환경의 성질이었다:

**`@cloudflare/vitest-pool-workers` v0.21은 D1을 테스트 사이에 되돌려주지 않는다.** (v3에 있던 `isolatedStorage` 옵션이 없어졌다. 프로브 테스트를 만들어 직접 확인했다 — 앞 테스트가 넣은 행이 다음 테스트에서 그대로 보인다.)

그래서 레이트리밋 카운터가 테스트·파일·실행에 걸쳐 계속 누적됐다. 처음엔 모든 테스트 클라이언트가 `CF-Connecting-IP` 없이 요청해 `unknown` 버킷 하나를 공유했고, IP를 순번으로 주도록 고쳤더니 이번엔 카운터가 파일마다 리셋되어 파일 간에 겹쳤다.

**해결**: 클라이언트마다 넓은 공간에서 무작위 IP를 뽑는다. 실행마다 새 IP라 누적되지 않는다. 레이트리밋 테스트 자신은 한도를 일부러 소진시키므로 아예 다른 대역(`172.16.x`)을 쓴다.

**검증**: 상태를 지우지 않고 8회 연속 실행해 전부 통과하는 것을 확인했다.

이건 앞으로 이 저장소에서 테스트를 쓸 때 반드시 알아야 할 성질이라 `인수인계.md`에도 적었다 — **테스트는 전역 개수를 단정하면 안 되고, 자기가 만든 데이터만 확인해야 한다.**
