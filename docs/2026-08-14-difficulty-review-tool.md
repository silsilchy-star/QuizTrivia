# 정답률 기반 난이도 보정 — 후보 탐지 도구

## 왜 이 작업을 했나

인수인계 문서의 "남은 일" 중 하나. `question_stats`(served_count/correct_count)는 계속 쌓이고 있었지만 이걸로 뭘 하는 로직이 없었다.

## 결정 (사용자에게 `AskUserQuestion`으로 확인)

1. **자동 반영 안 함.** 후보만 뽑아서 보여주고, 사람이 문항 본문을 읽어보고 납득한 것만 `data/questions/*.json`의 `difficulty`를 손으로 고친다.
2. **최소 표본 10건.** `served_count < 10`인 문항은 판단 대상에서 뺀다 — 우연히 몇 명이 다 맞히거나 틀려서 정답률이 튀는 걸 막는다.
3. **임계값은 합리적으로 결정**: 정답률 **90% 이상 → "너무 쉬움" 후보**(난이도 −1 제안), **30% 이하 → "너무 어려움" 후보**(난이도 +1 제안). 난이도 1을 더 내리거나 4를 더 올리는 제안은 하지 않는다(범위 밖이라 의미 없음).

## 무엇을 만들었나

`scripts/difficulty-review.mjs` (`npm run difficulty:review`)
- `wrangler d1 execute quiztrivia --remote --json`으로 `questions ⋈ question_stats`를 조회한다 (`--local` 플래그로 로컬 D1도 가능).
- 위 규칙대로 후보 두 그룹(너무 쉬움 / 너무 어려움)을 정답률 순으로 정렬해 출력한다. 문항 id, 현재→제안 난이도, 정답률(n/N), 공식/커뮤니티 구분, 본문 일부를 보여준다.
- **DB도 JSON도 건드리지 않는다.** 순수 리포트 도구.

로컬 D1에 가짜 `question_stats` 3건(과다 정답/과다 오답/표본 부족)을 넣고 `--local`로 돌려 분류 로직을 확인했다 — 표본 부족 건은 제외되고, 나머지 둘은 정확히 분류됐다.

## 다음에 이어서 할 사람이 할 일

프로덕션에 데이터가 충분히 쌓이면(며칠~몇 주) `npm run difficulty:review`를 돌려서 후보를 보고, 납득이 가는 것만 수동으로 `difficulty`를 고친 뒤 `npm run validate && npm test`로 확인하고 커밋한다. 이 스크립트 자체는 배포 파이프라인에 안 걸려 있다 — 사람이 필요할 때 로컬에서 실행하는 도구다.
