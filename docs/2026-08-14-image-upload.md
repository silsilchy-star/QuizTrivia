# 창작마당 이미지 직접 업로드 (R2)

## 요청

> "문제 제작 시 직접 첨부하는 방식으로 게임 이용하는 유저도 이미지를 올리기 쉽게 설계해주었으면"

**충족.** 기기에서 사진을 골라 바로 올릴 수 있게 했다. URL 붙여넣기도 그대로 남겨뒀다.

## 왜 필요했나

창작마당은 지금까지 **"이미 어딘가에 호스팅된 이미지의 URL"**만 받았다. 이건 두 가지 문제가 있다:

1. **문제를 만드는 사람에게 부담이다.** 사진을 어딘가에 먼저 올리고 링크를 따와야 한다. 휴대폰으로 찍은 사진을 쓰려면 사실상 불가능하다.
2. **남의 서버에 의존한다.** 링크가 언제 끊길지 모른다.

마침 같은 문제가 공식 콘텐츠에서도 드러났다 — "새 맞추기" 24문항이 전부 Wikimedia 핫링크이고, 이 작업 환경은 Wikimedia가 정책으로 차단돼 있어 새 문항을 만들 수 없다. 이미지를 직접 보관하면 그 의존이 끊긴다.

## 무엇을 했나

### 저장과 서빙 (`worker/images.ts`)

- **저장**: R2 버킷 `quiztrivia-images` (바인딩 `IMAGES`)
- **서빙**: 워커가 `/images/<키>`로 직접 내려준다

버킷을 공개로 열거나 별도 도메인을 붙이지 않았다. 워커가 서빙하면 프로비저닝이 버킷 하나로 끝나고, 접근 정책도 코드에서 관리된다.

**키는 내용의 SHA-256 해시**다(`<64자리 hex>.<확장자>`). 덕분에:
- 같은 사진을 여러 번 올려도 하나만 저장된다
- 키가 곧 내용이므로 `immutable` 캐시를 영구히 걸어도 안전하다
- 키를 추측해서 남의 이미지를 훑을 수 없다

### ⚠ 사용자 업로드를 같은 오리진에서 서빙하는 위험

이게 이 기능의 가장 조심스러운 부분이다. 사용자가 올린 파일이 우리 도메인에서 내려가면 XSS 통로가 된다. 세 겹으로 막았다:

**1) 선언된 타입을 믿지 않는다.** `Content-Type`과 확장자는 클라이언트가 마음대로 적을 수 있다. 실제 바이트의 매직 넘버로 판정한다.

```
JPEG  FF D8 FF
PNG   89 50 4E 47 0D 0A 1A 0A
GIF   "GIF8"
WebP  "RIFF" .... "WEBP"
```

`RIFF`로 시작하지만 WebP가 아닌 것(WAV 등)도 걸러진다.

**2) SVG를 아예 받지 않는다.** SVG는 이미지가 아니라 **스크립트를 품을 수 있는 문서**다. 같은 오리진에서 서빙하면 그대로 XSS가 된다. 매직 넘버 판정이 SVG를 통과시키지 않으므로 구조적으로 막힌다.

**3) 응답에 실행 차단 헤더를 붙인다.**
```
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; sandbox
```

### 그 밖의 제약

- **로그인 + 닉네임 필요** — 문항 생성과 같은 문턱
- **5MB 상한** — `Content-Length`로 먼저 거르고, 그 헤더는 거짓일 수 있으므로 실제 바이트 크기로 다시 본다
- **레이트리밋** — uid당 하루 200장 (`ADD_IMAGE`). 문항 수보다 넉넉하되 저장 용량이 무한정 늘지는 않게
- **서빙은 인증 없이 열려 있다** — 문항 이미지는 플레이 중 누구에게나 보여야 한다

### 검증 규칙 변경

`imageUrl`이 `https://`만 허용했는데, 이제 우리 업로드 경로도 받아야 한다. 두 가지만 허용한다:

```
/images/<64자리 hex>.(jpg|png|gif|webp)   ← 우리가 올린 것
https://…                                  ← 외부 링크
```

형태를 정확히 맞춘다 — `/images/../../etc/passwd`나 `/images/....svg` 같은 걸 통과시키면 안 된다.

### 화면 (`src/Workshop.tsx`)

"사진 선택" 버튼 → 파일 고르면 바로 업로드 → 미리보기 + "사진 빼기". 업로드 중에는 버튼이 잠기고, 실패하면 사유가 그 자리에 뜬다. 아래에 URL 붙여넣기 칸을 남겨 기존 방식도 계속 쓸 수 있다.

같은 파일을 다시 고를 때도 `onChange`가 뜨도록 input 값을 비운다(브라우저 기본 동작 때문에 안 그러면 두 번째 선택이 무시된다).

### 배포

`wrangler.jsonc`에 R2 바인딩이 생겼으므로 **버킷이 없으면 배포가 실패한다.** 파이프라인에 생성 단계를 넣되, 이미 있으면 넘어가고 **권한 부족 같은 진짜 실패는 그대로 드러나게** 했다(`|| true`로 덮지 않는다).

## 테스트 (22개)

무엇보다 **보안 성질**을 덮었다:
- 네 형식을 실제 바이트로 알아보는가 / SVG·HTML·빈 파일·짧은 조각을 거부하는가
- RIFF지만 WebP가 아닌 것을 거부하는가
- **Content-Type이 거짓이어도 실제 바이트를 따르는가** (png라 주장하는 jpeg → `.jpg`로 저장)
- 응답에 `nosniff`·CSP·`immutable`이 붙는가
- 형식에 맞지 않는 키(`../secret`, 짧은 키, `.svg`, hex 아닌 문자)가 R2를 건드리지도 않고 404인가
- 익명·닉네임 없음은 403인가, 세션 없으면 401인가
- 같은 파일 두 번 → 같은 경로인가
- 5MB 초과 413, 빈 파일 400
