# 문항 미디어: 이미지 링크 정비 + 유튜브 영상 첨부

## 요청

> "이미지, 영상을 등록하는 방식을 이미지 링크나 유튜브 링크로 대체할 수 없나"
>
> "이미지랑 유튜브 링크 첨부는 유저들이 직접 문제 만들 때에 확장성과 개방성을 위해서야. 이 구조만 탄탄하게 만들어주면 돼"

**충족.** 창작마당에서 이미지 링크와 유튜브 링크를 한 칸으로 받고, 영상 문항이 실제로 재생된다.

## 먼저 확인한 것 — 이미지 링크는 이미 되고 있었다

요청은 "링크로 **대체**"였지만, 코드를 보니 대체할 게 없었다. 이미 두 경로가 다 살아있다:

- 창작마당 UI에 `"또는 이미지 주소 붙여넣기 (https://…)"` 입력칸이 있다
- 서버 검증도 외부 https 링크를 명시적으로 허용한다
- 공식 "새 맞추기" 24문항은 **전부** Wikimedia 핫링크다

R2 업로드(`2026-08-14-image-upload.md`)는 링크를 **대체한** 게 아니라 **추가한** 것이었다. 인수인계 문서에 "Option C(R2 업로드)로 확정"이라 적혀 있던 건 제품의 제약이 아니라 **작업 환경의 제약**이었다 — 이 컨테이너에서 `commons.wikimedia.org`가 프록시 차단이라 에이전트가 새 이미지 URL의 유효성을 검증할 수 없다는 뜻이었지, 유저가 링크를 못 쓴다는 뜻이 아니었다. 실제로 사용자는 2026-08-14에 브라우저로 24장 전부 정상임을 확인했다.

그래서 이번 작업의 실제 내용은 **(a) 느슨했던 이미지 링크 검증을 조이고, (b) 없던 영상 지원을 만드는 것**이 됐다.

## ⚠ 고쳐야 했던 허점 — "https로 시작하면 통과"

기존 이미지 검증은 이랬다:

```ts
if (!isUploadedImagePath(url) && !/^https:\/\/.+/.test(url)) { ... }
```

`https://` 뒤에 뭐가 오든 통과한다. 그래서 **유튜브 링크를 이미지 칸에 붙여넣으면 검증을 통과해 저장되고, 화면엔 깨진 이미지 아이콘이 떴다.** 유저 입장에선 아무 설명 없이 실패하는 것이라 이번에 같이 잡았다.

이제 문자열 정규식이 아니라 URL 파서로 판정한다:

| 검사 | 이유 |
|---|---|
| `new URL()` 파싱 성공 | 형태가 URL이 아닌 것 배제 |
| `protocol === 'https:'` | `javascript:` · `data:` · `blob:` 를 한 번에 막는다 |
| `username`/`password` 없음 | `https://진짜주소@가짜주소/` 는 호스트를 잘못 읽게 만든다 |
| 유튜브 링크면 거부 | 영상 칸으로 안내 (조용히 깨지는 대신) |

**호스트는 일부러 열어뒀다.** 어디에 올린 사진이든 붙일 수 있어야 한다는 게 이 기능의 목적(개방성)이라, 허용 목록을 두지 않았다.

## 영상 — 유튜브 링크

### 설계의 핵심: 유저가 준 URL을 iframe src에 넣지 않는다

영상은 iframe으로 재생된다. 즉 **유저가 준 문자열이 우리 화면 안에서 남의 페이지를 띄우는 경로**가 된다. 여기서 URL을 그대로 흘려보내면 그 자체가 공격면이다.

그래서 URL을 저장하지 않는다. 링크에서 **영상 id만 뽑아** 저장하고, 실제 임베드 주소는 우리가 조립한다:

```
유저 입력   https://www.youtube.com/watch?v=dQw4w9WgXcQ&list=PL123&t=42s
     ↓ 파싱 (id만 추출, /^[A-Za-z0-9_-]{11}$/ 로 검증)
저장        video_kind='youtube', video_id='dQw4w9WgXcQ'
     ↓ 조립 (src/media.ts의 youTubeEmbedUrl)
iframe src  https://www.youtube-nocookie.com/embed/dQw4w9WgXcQ?rel=0&playsinline=1
```

저장되는 값이 11자 URL-safe base64로 강제되므로, **구조적으로** 위험한 문자가 들어갈 수 없다. 유저가 붙인 `list=` 같은 파라미터도 임베드 주소로 새어나가지 않는다.

읽을 때도 다시 검증한다(`videoFromStored`). 어떤 경로로든 DB에 이상한 값이 들어갔다면 iframe까지 흘러가는 대신 그냥 영상 없는 문항이 된다.

### 파서는 하나뿐이다 — `src/media.ts`

프론트와 워커가 **같은 파일**을 쓴다. 창작마당은 사람 검수가 없어서 이 파서가 사실상 유일한 방어선인데, 규칙을 두 곳에 따로 쓰면 언젠가 어긋나고 그때 느슨한 쪽이 뚫린다. `src/types.ts`가 순수 타입만 두어 양쪽에서 include되는 것과 같은 이유다.

받는 형태: `watch?v=` · `youtu.be/` · `/shorts/` · `/embed/` · `/live/` · `/v/`, 호스트는 `youtube.com` · `www` · `m` · `music` · `youtube-nocookie.com`.

### 임베드 옵션

- `youtube-nocookie.com` — 재생 전에는 추적 쿠키를 심지 않는 도메인
- `rel=0` — 끝나고 남의 채널 영상을 추천하지 않게. **문제 화면에 엉뚱한 썸네일이 뜨면 그 자체가 스포일러가 될 수 있다.**
- `playsinline=1` — iOS에서 전체화면으로 튀지 않는다
- `allow`에 **autoplay를 넣지 않았다** — 문항이 열리자마자 소리가 나면 안 된다

## 스키마

`migrations/0001_add_question_video.sql` — `questions`에 `video_kind`, `video_id` 두 컬럼 추가.

`db/schema.sql`은 **건드리지 않았다.** 그 파일은 배포마다 재실행되는 멱등 베이스라인이라, (a) 이미 테이블이 있는 프로덕션에서는 한 줄도 안 돌아 컬럼이 안 생기고, (b) 반대로 `CREATE TABLE`에 컬럼을 넣어두면 빈 DB에서 이 `ALTER`가 `duplicate column name`으로 깨진다. `schema.sql → migrations` 순서로 적용하면 기존 DB든 새 DB든 같은 모양으로 수렴하고, `npm test`가 매번 (b)를 검증한다(`test/setup.ts`).

`video_kind`에 CHECK 제약은 걸지 않았다. 값을 늘릴 때마다 D1에서 테이블 재생성이 필요해지는데(`migrations/README.md`) 그 비용이 얻는 것보다 크다. 대신 읽을 때 코드가 검증한다.

## UI — 칸 하나로 받는다

이미지 칸과 영상 칸을 따로 두는 대신, **붙여넣기 칸 하나**가 둘 다 받는다. 유튜브 주소면 영상, 아니면 이미지로 판정한다. "이건 이미지입니다"를 유저가 직접 고르게 하는 건 불필요한 질문이다.

판정은 서버와 같은 파서를 쓰고, 최종 판단은 어차피 서버가 다시 한다 — 클라이언트 판정은 미리보기와 라우팅 편의일 뿐 신뢰 대상이 아니다.

**한 문항에 이미지와 영상을 함께 붙일 수는 없다.** 화면에서 뭘 먼저 보여줄지가 애매해지고 문제를 읽기도 어려워진다. 서버가 거부한다.

## 공식 콘텐츠는 영상을 지원하지 않는다

`scripts/*.mjs`는 평범한 Node ESM이라 TypeScript인 `src/media.ts`를 import할 수 없다. 공식 파이프라인까지 지원하려면 같은 파서를 JS로 한 벌 더 써야 하는데, **"파서는 하나"라는 전제가 이 기능의 안전성을 떠받치고 있어서** 그걸 깨지 않기로 했다.

대신 조용히 무시되지 않게 `scripts/validate.mjs`가 `videoUrl`이 있으면 ERROR를 낸다. 이번 요청도 애초에 "유저들이 직접 문제 만들 때"가 목적이라 범위가 맞는다.

## 남은 것 / 알아둘 것

- **영상 안에 답이 나오면 `scripts/fairness.mjs`의 정답 노출 방어가 통하지 않는다.** 그 규칙은 문항 본문 텍스트만 본다. 영상 내용은 기계가 볼 수 없으니 구조적으로 못 막는 구멍이다. 창작마당은 원래 랭킹에 반영되지 않으므로 피해 범위는 그 주제 안에 갇힌다.
- **영상이 삭제·비공개되면 문항이 죽는다.** 이미지 핫링크와 같은 문제이고, 영상은 더 자주 사라진다. R2 업로드처럼 우리가 보관할 수 있는 성질이 아니라 감수해야 하는 부분이다.
- 브라우저에서 실제 재생되는지는 배포 후 사용자 확인이 필요하다 — 이 작업 환경은 유튜브를 포함한 외부 호스트가 프록시 차단이라 여기서는 확인할 수 없다.
