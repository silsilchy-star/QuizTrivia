# R2 이미지 업로드 제거 — 하루 넘게 막혀 있던 배포 복구

## 무슨 일이 있었나

PR #1을 머지한 뒤 배포가 실패했다. 로그를 파보니 **이번이 처음이 아니었다.**

| 배포 | 커밋 | 결과 |
|---|---|---|
| 2026-08-14 01:49 | `a28f0aa` 문항 공정성 | ✅ **마지막 성공** |
| 2026-08-14 02:05 | `e90083b0` R2 이미지 업로드 | ❌ |
| 2026-08-14 07:49 | `ed81ba4` 난이도 도구 | ❌ |
| 2026-08-15 06:24 | `21444c8` PR #1 머지 | ❌ |

세 번 다 같은 오류다:

```
✘ [ERROR] A request to the Cloudflare API (/accounts/***/r2/buckets/quiztrivia-images) failed.
  Please enable R2 through the Cloudflare Dashboard. [code: 10042]
```

`wrangler.jsonc`에 R2 바인딩이 선언돼 있는데 **계정에 R2 자체가 켜져 있지 않았다.** R2를 도입한 그 커밋부터 배포가 깨졌고, 아무도 알아채지 못한 채 프로덕션은 하루 넘게 08-14 01:49 버전으로 멈춰 있었다.

### ⚠ 그래서 "이미지 직접 업로드"는 한 번도 라이브였던 적이 없다

인수인계에 `~~진짜 이미지 파일 업로드~~ ✅`로 적혀 있었지만 **사실이 아니었다.** 코드는 머지됐고 테스트도 통과했지만, 그 코드를 실은 배포가 실패해서 프로덕션 워커에 올라간 적이 없다. **"머지됨"과 "라이브"를 같은 것으로 적은 게 이 문서의 오류였다.**

## 두 번째 문제 — 실패를 가려버린 가드

배포 워크플로에는 R2 버킷을 확인하는 단계가 있었고, 주석에는 이렇게 적혀 있었다:

> 권한 부족 같은 진짜 실패는 그대로 드러내야 하므로 `|| true`로 덮지 않는다.

그런데 코드는 정반대로 동작했다:

```bash
if npx wrangler r2 bucket create quiztrivia-images 2>&1 | tee /tmp/r2.log; then
```

**bash 파이프라인의 종료 코드는 마지막 명령(`tee`)의 것이다.** `tee`는 항상 성공하므로 wrangler가 무슨 오류를 내든 `if`가 참이 되어 "버킷 생성됨"을 찍고 넘어간다. 준비해둔 진단 메시지(`::error::R2 버킷을 만들 수 없다...`)는 **한 번도 출력된 적이 없고**, 실패는 세 단계 뒤 `wrangler deploy`에서 맥락 없는 오류로 튀어나왔다.

이번에 R2를 걷어내면서 이 단계째로 삭제했다. 앞으로 워크플로에서 파이프라인의 성공 여부를 판정해야 하면 `set -o pipefail`을 쓰거나 `${PIPESTATUS[0]}`을 봐야 한다.

## 세 번째 문제 — DB만 앞서가고 워커는 뒤처진다

배포 단계 순서는 이렇다:

```
검증(typecheck·test·validate·빌드) → D1 백업 → D1 스키마·마이그레이션·seed → 워커 배포
```

인수인계 7번은 "검증이 전부 먼저, DB 변경이 그 다음"이라고 적고 있는데, 이건 **검증 실패**만 막아준다. `wrangler deploy` 자체가 실패하면 **DB는 이미 앞서간 뒤**다.

실제로 이번 머지에서 그렇게 됐다 — 마이그레이션 0001·0002가 프로덕션에 적용되어 영상 컬럼이 생기고 birds 데이터가 삭제된 상태에서, 워커만 08-14 버전으로 남았다.

이번엔 피해가 없었다. 새 컬럼은 추가만 된 것이라 옛 워커가 읽지 않고, birds는 `draft`라 원래 목록에 안 보였기 때문이다. 하지만 **컬럼을 지우거나 이름을 바꾸는 마이그레이션이었다면 옛 워커가 곧바로 깨졌을 것이다.** 이 성질을 알고 마이그레이션을 써야 한다 — 새 스키마는 항상 **옛 워커도 견딜 수 있게**(추가 위주로) 만드는 게 안전하다.

## 결정: R2를 걷어내고 링크만 남긴다

두 가지 길이 있었다.

1. Cloudflare 대시보드에서 R2를 활성화 (2분, 약관 동의·결제수단 필요)
2. R2 바인딩과 업로드 기능을 들어내고 링크만으로 간다

**사용자가 2번을 택했다.** 애초에 이번 방향의 목적이 "유저가 문제 만들 때 이미지·유튜브 **링크**를 붙이는 확장성·개방성"이었고, 링크는 R2 없이 동작한다. 기기 업로드는 어차피 한 번도 라이브였던 적이 없는 기능이라 잃는 것이 사실상 없다.

| 파일 | 내용 |

| `test/images.test.ts` | 삭제 |

**남은 것**: 외부 https 이미지 링크, 유튜브 영상 링크. 창작마당의 붙여넣기 칸은 그대로이고 "사진 선택" 버튼만 사라졌다.

프로덕션 DB에 `/images/...` 값이 든 행은 없다 — 업로드가 라이브였던 적이 없으므로 만들어질 수 없었다. 마이그레이션이 필요 없는 이유다.

## 검증

- `npm test` **211개 통과** (239 → −28: `test/images.test.ts` 22개 + `media.test.ts`의 업로드 경로 6개)
- `npm run typecheck` · `npm run validate` · `npm run build` 통과
- `npx wrangler deploy --dry-run` — 바인딩이 `DB`(D1)와 `ASSETS`만 남은 것을 확인. **R2 바인딩이 없으므로 이번 배포는 같은 이유로 실패하지 않는다.**
- `python3 -c "import yaml; yaml.safe_load(...)"` 로 워크플로 파싱 확인 (인수인계 11번)

## 나중에 R2가 필요해지면

계정에 R2를 켠 뒤 이 커밋을 되돌리면 된다. 업로드 구현은 git 이력에 그대로 있고, 특히 `worker/images.ts`의 **매직 넘버 형식 판정 + SVG 차단 + nosniff·CSP** 세 겹 방어는 같은 오리진에서 사용자 파일을 서빙할 때 반드시 필요한 것이니 다시 쓸 때 그대로 살려야 한다 (`docs/2026-08-14-image-upload.md`).
