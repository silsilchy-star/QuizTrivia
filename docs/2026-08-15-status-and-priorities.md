## 2. 이번 작업 흐름에서 한 것

### 2-1. 방향 전환 — "새 맞추기 완성"에서 "유저 창작 확장성"으로

세 세션째 24/80에서 멈춰 있던 "새 맞추기"(birds) 주제를 **주제째 제거**했다. 사용자 정리: *"새 맞추기에 집착하지 말고 리스트 없애 / 이미지랑 유튜브 링크는 유저들이 직접 문제 만들 때 확장성과 개방성을 위해서다 / 이 구조만 탄탄하게 만들어주면 된다."*

이게 이번 흐름 전체의 기준선이 됐다. 미디어 첨부는 **특정 주제를 완성하기 위한 수단이 아니라 유저 창작의 개방성**을 위한 것이다.

JSON에서 빼는 것만으론 프로덕션에 고아 행이 남아서 `migrations/0002`가 FK 순서대로 지운다. (`2026-08-15-remove-birds-topic.md`)

### 2-2. 창작마당 미디어 — 이미지 링크 + 유튜브 영상

붙여넣기 칸 **하나**가 이미지 링크와 유튜브 링크를 모두 받는다. 유튜브 주소면 영상 문항이 된다.

보안 설계가 핵심이다. **유저가 준 URL을 iframe·img의 src에 그대로 넣지 않는다.** 유튜브는 링크에서 **영상 id 11자만 뽑아** 저장하고(`video_kind`/`video_id`) 임베드 주소는 우리가 조립한다. 저장값이 URL-safe base64 11자로 강제되니 위험한 문자가 구조적으로 못 들어간다.

**파서는 `src/media.ts` 하나뿐이고 프론트와 워커가 같이 쓴다.** 규칙을 두 벌 두면 어긋나는 날 느슨한 쪽이 뚫린다. 예전 이미지 검증(`/^https:\/\/.+/`)은 사실상 아무것도 못 걸러서 유튜브 링크가 이미지로 저장돼 깨진 이미지가 뜨고 있었다 — 이것도 URL 파서로 교체했다. (`2026-08-15-media-links-youtube.md`)

### 2-3. 내 문항 목록 + 개별 삭제

작성자가 자기 문항을 보고 하나씩 지울 수 있다. 수정은 없다 — 지우고 다시 넣는다.

⚠ **이 목록에는 정답·해설이 들어 있어 작성자 본인에게만 내려간다.** 남이 볼 수 있으면 그 주제는 정답표 펴놓고 푸는 것과 같다. `test/community.test.ts`가 이 경계를 지킨다. 추가와 삭제가 게이트 규칙을 서로 다르게 계산하지 않도록 `recountTopic()`으로 묶었다. (`2026-08-15-my-questions-list-and-delete.md`)

### 2-4. R2 업로드 철회 — 하루 넘게 막혀 있던 배포 복구

**배포가 세 번 연속 조용히 실패하고 있었다.** `Please enable R2 through the Cloudflare Dashboard [code: 10042]` — 계정에 R2가 켜져 있지 않았다. 마지막 성공 배포는 08-14 01:49였고 그 뒤 24시간 넘게 아무것도 라이브에 못 올라갔는데 아무도 몰랐다.

가드 코드가 있었는데도 못 잡았다. `if cmd 2>&1 | tee log; then` 은 파이프라인의 종료 코드가 `tee`의 것이라 **항상 참**이다. 준비해둔 진단 메시지가 한 번도 출력되지 않았다.

사용자 결정은 **"R2 빼고 링크만으로 가기"**. 기능을 걷어내 배포를 복구했다. 다시 넣으려면 대시보드에서 R2를 켠 뒤 그 커밋을 되돌리면 된다. (`2026-08-15-remove-r2-upload-unblock-deploy.md`)

### 2-5. sports 좁은 주제 5개 = 320문항

구기 54 · 축구 62 · 올림픽 63 · 야구 70 · 기록 71을 다섯 배치로 넣어 **전부 `active`**로 올렸다. 플레이 가능한 주제가 3개 → 8개가 됐다.

작업 중 **앞선 추정이 틀렸다는 걸 발견했다.** 인수인계에 "문항 하나가 좁은 태그를 2개까지 다니 520개면 된다"고 적혀 있었는데, 기존 데이터는 문항마다 좁은 태그가 **정확히 1개**이고(sports 80문항 = 18+26+17+10+9, 조합 태그 0건) 태그들이 의미상 배타적이다. `구기`는 축구·야구를 뺀 나머지, `기록`은 비구기 종목이다. 억지로 2개를 달면 주제 겹침 규칙에 걸리고 플레이어가 같은 문항을 두 주제에서 다시 본다. **슬롯 1개 ≈ 문항 1개**로 정정했고, 남은 규모는 520이 아니라 720이다.

난이도 3은 상상해서 만들지 않았다. **규칙이 실제로 개정돼 옛 규칙으로 배운 세대가 실재하는 항목**으로만 채웠다 — 탁구공 38→40mm, FIBA 3점 라인 6.25→6.75m, 골프 깃대 꽂고 퍼팅 허용(2019) 같은 것들. 100문항 전부에 `seedRef`를 달았다.

### 2-7. 배포를 두 번 막은 것

**① CI 간헐 실패.** 같은 커밋의 두 실행이 하나는 실패, 하나는 통과했다. `git diff origin/main..HEAD -- test/`가 비어 있어 회귀가 아님을 먼저 확정했고, 원인은 요청을 순차로 수십 번 보내는 테스트(게이트 20회, 레이트리밋 101회)가 vitest 기본 5초를 넘긴 것이었다. `testTimeout` 20초로 해결. 배포 워크플로도 `npm test`를 관문으로 쓰기 때문에 방치하면 그대로 배포 실패가 된다.

**② `SQLITE_TOOBIG`.** 머지 직후 배포가 `Apply D1 seed`에서 멈췄다. `build-seed.mjs`가 승인 문항 **전체를 여러 행 INSERT 한 문장**으로 뽑는데, 문항이 240 → 560개가 되자 그 문장이 **224,693바이트**가 됐다. D1 한도는 100KB.

코드는 한 줄도 안 바뀌었고 **문항만 늘렸는데 배포가 깨졌다.** 콘텐츠가 늘어나면 언젠가 반드시 터지도록 예약돼 있던 실패다.

두 겹으로 고쳤다 — `chunkedInsert()`가 40KB 예산으로 문장을 쪼개고(224KB 한 문장 → 40KB 이하 다섯 문장), 생성 직후 100KB를 넘는 문장이 있으면 **파일을 쓰지 않고 exit 1** 한다. `Build seed from JSON`은 DB를 건드리기 전 단계라 같은 문제가 다시 생기면 프로덕션 근처에 못 간다. (`2026-08-15-seed-statement-too-big.md`)

## 3. 이번에 드러난 구조적 문제

기능 버그가 아니라 **파이프라인의 성질**이라 앞으로도 계속 물릴 것들이다.

1. **콘텐츠가 늘면 배포가 저절로 깨질 수 있다.** 코드를 안 건드려도 문항 수가 임계를 넘는 순간 터진다. `SQLITE_TOOBIG`이 그랬고, NUMERIC 비율 하한 이탈도 같은 성질이다. → seed 크기는 이제 빌드 가드가 막는다. 비율은 배치마다 눈으로 확인해야 한다.

2. **배포가 실패해도 DB는 이미 앞서간 상태다.** 단계 순서가 `검증 → DB 스키마·마이그레이션·seed → 워커 배포`라, 워커 배포가 실패하면 "DB는 새 스키마, 워커는 옛 버전"이 된다. 이번 `SQLITE_TOOBIG` 때는 적용할 마이그레이션이 없어서 물리지 않았을 뿐이다. → **마이그레이션은 옛 워커도 견딜 수 있게 쓴다.** 컬럼 추가는 안전하고, 삭제·이름 변경은 곧바로 프로덕션을 깨뜨린다.

3. **실패를 아무도 모른다.** R2 건은 24시간 넘게 방치됐다. GitHub의 기본 실패 메일은 이미 가고 있었지만 실제로는 눈에 띄지 않았다. → 이번 두 건은 능동적으로 지켜봤기 때문에 잡혔다. 사람이 안 볼 때 머지되면 같은 일이 반복된다. (아래 우선순위 "보류" 참고)

## 5. 우선순위 제안

### 1순위 — sports d3 100문항 사실 검수

**이유는 두 가지고, 두 번째가 더 중요하다.**

첫째, 이 문항들은 **이미 라이브**다. 연도나 수치가 틀리면 맞게 답한 플레이어를 틀렸다고 채점한다. 퀴즈 앱에서 이건 기능 장애와 같다.

둘째, **같은 방식으로 720문항을 더 만들 참이다.** 난이도 3을 "실제로 개정된 규칙"으로 채우는 접근이 실제로 정확한지 지금 한 번 검증해두지 않으면, 오류가 있을 경우 그 오류를 앞으로 8배로 복제하게 된다. 이건 콘텐츠 점검이 아니라 **방법론 점검**이다.

지금 이 환경에서 웹 검색이 되는 것을 확인했다(FIBA 14초 룰 = 2014년으로 교차 확인됨). 즉 사용자 손을 빌리지 않고 진행할 수 있다. 100문항이면 반나절 규모다.

### 2순위 — geography 320문항

가시적 성과가 가장 크다. 활성 주제 **8 → 13개**. sports에서 다섯 배치를 돌려 방식이 이미 검증됐고, 검수 도구(유사 중복 검출기)도 그대로 재사용한다.

science보다 먼저인 이유는 단순히 더 싸기 때문이다 — 320 대 400, 그리고 지리 쪽 d3 결손이 더 적다.

### 3순위 — `ACCEPT_LEGACY` 닫기

보안 항목이고 예정일(≈08-27)이 가까워지고 있다. 작업 자체는 플래그 하나와 테스트 확인으로 30분이면 끝난다.

콘텐츠보다 뒤에 둔 이유: 유저가 16명뿐이고 `/api/session`이 접속할 때마다 서명 쿠키로 자동 갱신하므로, 08-13 이후 한 번이라도 들어온 사람은 이미 갈아탔다. 급히 당길 실익이 크지 않다. 다만 **예정일을 넘기지는 말 것.**

### 4순위 — science 400문항

마지막 묶음. 끝나면 활성 주제 19개로 D-16 계획이 완결된다.
